# P3B V1 云存档范围收缩审计

日期：2026-09-16

## 产品结论

- V1 需要跨设备恢复的唯一模块是 `user`。
- `settings`、`tutorial`、`task`、`activitys` 继续使用设备本地存档，第二版再按实际需求评估。
- `record` 没有 `dataKey`，原实现本就不会进入统一导出；V1 不新增局内续玩云同步。

## 代码审计

- 前端没有上述模块各自独立的后端接口；它们只是通过 `dataKey` 被通用 `ControllerManager.getUserStorage()` 聚合。
- 原 `ServerController` 使用通用全模块导出、全控制器脏标记和全量恢复，产品范围实际由通用机制间接扩大，并非明确业务需求。
- `ControllerManager.forceSave()` 会立即落盘所有 DAO。若 `saveImmediately()` 再设置服务端脏标记，退后台和测试刷新就会把纯本地模块误判为待上传。
- `SECRET_DAO_ON_SAVED` 会更新 `user.saveTime`。该更新时间只用于本地完整性和存档新旧判断，不能因本地模块落盘而制造一次 `user` 云变更。

## 兼容与风险决定

- 前端上传和恢复都只处理 `modules.user`；读取旧五模块云档时忽略其他云端模块，保留设备本地值。
- 后端仍校验旧模块中的危险结构和总请求大小，再把数据归一化为 `modules.user`，避免旧客户端立即失效，也避免被丢弃字段绕过输入限制。
- 缺少对象类型 `user` 的请求拒绝；未知模块继续拒绝。
- 现有文档会在下一次成功 PUT 时自然变为 user-only，不做高风险批量迁移。
- 管理后台计划同步缩小：V1 不承诺查询或管理本地模块。
