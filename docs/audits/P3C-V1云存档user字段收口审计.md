# P3C V1 云存档 user 字段收口审计

日期：2026-09-18

## 现象与证据

- 微信开发者工具中的 `PUT /v1/save` 请求体已经只包含前端 V1 白名单字段。
- 同一玩家成功写入新 revision 后，`GET /v1/save` 的当前 `save.modules.user` 仍返回请求中已省略的旧字段。
- 因此前端构建和上传筛选不是本次残留的原因，问题位于服务端持久化更新语义。

## 根因

- `CloudBaseCloudSaveRepository` 使用 `_id + revision` 条件查询后调用 `update()`，CAS 并发保护正确。
- CloudBase 对嵌套对象执行递归合并；普通对象形式的 `save` 不会删除数据库内本次请求未携带的子键。
- 原服务端只把模块收口为 `modules.user`，没有对 user 内部字段再次做白名单，旧客户端仍可能重新提交废弃字段。

## 修复决定

- 保留 `_id + revision` 条件更新，不改成无条件 `doc.set()`，避免破坏多设备冲突保护。
- 使用官方 SDK 的 `db.command.set()` 在同一次条件更新中整体替换 `save` 和 `previous`。
- 服务端增加与微信前端一致的 29 个 user 字段白名单；先完成原始请求的大小、深度、危险键等校验，再过滤未知字段并计算最终 hash/size。
- 首次插入仍使用普通对象；只有已有文档的条件更新需要替换指令。

## 数据与兼容性

- 不迁移、不批量修改真实玩家文档；每个玩家在修复版本部署后的下一次成功 PUT 会自然清理当前 `save`。
- 当次 PUT 的 `previous` 保留更新前的真实上一版快照；再完成一次 PUT 后，上一版也会自然来自已收口的当前版。
- API 路径、请求外层结构、成功响应、错误码、数据库顶层结构和 CAS 规则均不变化。
- 未更新的旧客户端可以继续调用，但其白名单外 user 字段会被忽略，这是当前开发阶段明确接受的数据收口行为。

## 安全提醒

- 调试网络面板截图不得包含完整 `Authorization` Bearer Token；已暴露的开发会话应通过重新登录更新，验收材料必须遮盖 token。

## 验收门槛

1. typecheck、lint、全部测试、build、`git diff --check` 通过。
2. 自动测试证明服务端 user 白名单和 CloudBase `set` 指令被使用。
3. 真实 CloudBase 临时探针先写入废弃字段，再以省略字段的下一 revision 更新，读取当前版时废弃字段不存在，探针最终自动删除。
4. 中文提交并推送；CloudBase Git 平台更新部署。
5. 微信真实玩家再成功 PUT 一次，随后 GET 当前版只包含 29 个白名单字段。
