# P5B1 微信头像昵称资料审计

## 审计结论

- 前端 `PlayerState` 已有 `nickName/avatarUrl`，但原“刷新昵称”按钮仅随机生成猫昵称，`saveUserInfo` 仍是禁用桩。
- 昵称头像已在 P3C 从玩法云存档白名单移除，不能重新塞回 `modules.user`。
- 项目微信 typings 明确提供 `wx.createUserInfoButton`；小游戏中不能依靠 `wx.authorize(scope.userInfo)` 自动弹窗，因此必须由用户点击原生按钮主动触发。
- 首页和资料弹窗已有头像/昵称展示位，无需修改 FairyGUI 资源包。

## 冻结契约

- 玩家 API：`GET /v1/profile`、`PUT /v1/profile`，均使用现有 Bearer 会话。
- 数据：`player_profiles/{playerId}`，只含 `nickName/avatarUrl/updatedAt`。
- 昵称 1～32 个 Unicode 字符并拒绝控制字符；头像为空或 HTTPS URL，最长 2048 字符。
- 请求日志脱敏昵称与头像 URL；不收集性别、城市、省份、加密资料或图片二进制。
- 登录后读取一次；用户主动授权后写入一次，不轮询、不随云存档定时上传。

## 降级与成本

- 未授权、取消、平台失败、资料 GET/PUT 失败均继续使用本地资料并正常进入游戏。
- 每个玩家最多一条小文档，正常冷启动至多一次读取、主动更新一次写入，适合当前免费/低配资源限制。
- 微信头像 URL 失效时显示项目默认头像，用户可再次主动同步。

## 管理后台影响

- 后台计划增加独立资料区，只读、按权限查看；不把资料归入云档回滚。
- 列表默认不加载头像，不开放资料批量导出或按昵称模糊遍历。
- 管理后台仍须使用独立管理员 API/RBAC，不能复用玩家 Bearer 接口。
