# 2026-11-07 服务端提交说明

## 提交范围

本次将服务端目录此前尚未提交的版本控制与主线云存档相关改动统一交付到 `main`，基线为 `2dc6f4c`。客户端冷启动提速和管理后台前端属于各自工程，不包含在此服务端提交中。

## 1. 项目设置与版本控制

- 新增 `GET /admin/v1/project-settings/version-control` 和 `PUT /admin/v1/project-settings/version-control`。
- 沿用管理员 Cookie、来源校验和权限体系：配置读取权限可查看，配置发布权限可修改。
- 页面只需填写最新版本与最低可用版本；后端校验三段数字版本及最低版本不高于最新版本。
- 每次有效修改自动递增 `revision` 并记录操作审计。原子 CAS 校验拒绝过期表单和并发覆盖，返回 409。
- 保存只修改版本字段，保留维护和云存档开关；未改动的设置不重复写入。
- 若规则已写入但审计失败，明确提示“设置已保存”，避免误判为未生效。
- 公共 `/v1/bootstrap-config` 增加 `latestClientVersion`，旧记录缺字段时返回空字符串；原有响应字段保留。
- 命令行发布工具保留 dry-run 和显式发布开关，写入同样使用 CAS。

## 2. 80 关主线进度与云档保护

当前代码策略明确为：

| 策略 | 值 |
|---|---|
| 存档批次 generation | `mixed99-20261105` |
| 关卡进度版本 levelProgressVersion | `rhythm80-20261106` |
| 首个可玩关卡 | 第 `6` 关 |

- `/health` 返回当前存档批次、进度版本和不含凭据的持久化目标指纹，便于部署及维护工具核对目标。
- 读取其他批次云档时向客户端呈现当前批次尚无云档，不自动删除旧文档。
- 写入不匹配批次/进度版本时，分别返回 `SAVE_GENERATION_MISMATCH` / `SAVE_PROGRESS_VERSION_MISMATCH`；非法低关卡也会被拒绝。
- 扩展现行 user 白名单，保留必要的游戏次数和进度版本字段。
- 客户端仍只能写入白名单字段；仓储在相同批次、相同 revision 的 CAS 内合并当前存档，保留已存在的其他模块、未知资产和请求省略字段。
- 动物资产原样保留；正常保存不再顺带运行历史动物清理。
- 合并后重新计算存档摘要与字节数，并保留原始请求的幂等身份。
- 维护和后续保存对 current/previous 快照使用一致的关卡迁移策略，保留非进度资产。

这些策略此前已在本地开发和维护中使用；本次提交不会自动运行迁移或清档。较旧客户端如果缺少上述批次标记，保存仍会受到策略限制，不能把部署本提交理解为所有旧包都可正常同步云档。

## 3. 排行榜兼容与并发处理

- 排行榜投影只接受指定存档批次和进度版本的记录。
- 进度迁移时保留符合新进度版本的已推进关卡，避免重复运行工具把新版进度拉回起点。
- 投影和重置涉及并发时使用条件更新与同步标记，避免旧批次或迟到任务覆盖已经迁移的结果。
- 提交前审阅补充修复：迁移遇到孤立排行榜记录时，精确识别缺失云档，备份后跳过并以 `leaderboardOrphans` 报告；权限或网络错误仍中止操作，不冒充缺失记录。

## 4. 手动维护工具

- `save:reset-progress:wechat`：只迁移关卡进度，保留金币、体力、动物、其他模块和 previous 中的非进度资产；写入前逐条备份并同步落盘，CAS 冲突不会强行覆盖。
- `save:reset-development:wechat`：开发期统一清理工具，范围固定为 `cloud_saves` 与 `level_leaderboard`，不接收任意集合名。
- 两个工具默认 dry-run。执行 `--apply` 前必须核对线上健康接口的批次与数据库目标指纹；进度迁移还检查进度版本并生成独立备份和报告。
- Docker 发布镜像只编译/运行服务，不包含也不自动调用这些维护脚本。
- 本次提交推送不执行以上命令，不重复历史清档，不修改任何线上玩家数据。

历史维护说明及匿名统计记录一并纳入版本管理，记录的是当时的操作，不是本次提交新执行的操作。
